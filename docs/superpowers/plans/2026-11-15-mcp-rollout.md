# MCP upgrade migration, validation and rollback

Candidate only; no deployment or customer/provider mutations authorized. Apply additive migrations `20261115160000_agent_credentials` and `20261115160000_mcp_publication_fence` before new code. No key backfill/rotation. Retain tables, verifier/revocation metadata, attempt receipts and fences on rollback.

New MCP jobs persist `Post.mcpWorkflowVersion=114` before enqueueing. Creation, approval, edit restart and missing-post sweep route through that stamp; original workflow definitions/signatures remain unchanged. Worker admission and API cancellation share the database fence. Workflow authority includes generation and payload hash, so a stale sleeping worker cannot publish a later revision. STARTED without durable receipt remains UNKNOWN. No shipped provider claims terminal reconciliation support; unsupported recovery stays blocked. Test adapters must prove terminal unpublished results, not merely absent receipts.

Roll back exposure and new admissions first. Retain a worker image capable of V114 and its activities until tracked jobs drain or are safely fenced/reconciled. Old-image-only rollback is unsafe. Do not restore an old database backup over current revoked credentials or publication receipts. Do not drop additive schema while any new-code worker or tracked job remains.

Organization agent saves hold a durable admission across quota checks and writes, including a multi-channel tool batch. Each row identifies its server instance, host, PID and unique request owner, and its committed post IDs are recorded in the same transaction as each saved thread. Recovery in Settings > Agent access performs an audited compare-and-fence transaction for the exact visible owner: it waits for any admitted save transaction to settle, inventories committed posts, removes only that owner and records the existing ActivityLog identity plus an owner/post reconciliation receipt. Every later post save by the old request must lock and match the same owner inside its write transaction, so a recovered owner cannot resume writing even if still alive. No TTL or process-death guess is used. Previously accepted saved/scheduled jobs stay active; already-running short-link preparation may finish but cannot authorize another post save. Recovery audit identity uses the existing user-erasure handling.

New MCP roots, initial revision fences and workflow version stamps commit together before QUEUE visibility. Confirmed segment receipts and their PUBLISHED projections also commit in one shared-fence transaction. Cancellation discloses preserved published segments and returns PARTIALLY_UNSCHEDULED or ALREADY_PUBLISHED as appropriate. Human approval of a cancelled remainder keeps published receipts and approves only the current unpublished revision. Workflow dispatch uses mcp-publish-v114; publication activities use mcp-v114-<provider> queues with the existing per-provider concurrency cap/divider. Old binaries never poll these queues. Recovery distinguishes that generation's actual Temporal status from an ACTIVE database fence, with network/status uncertainty remaining UNKNOWN.

Hosted CI uses disposable PostgreSQL schemas only: `agent_credentials` for credential lifecycle and `mcp_publication` for durable admission/fence races. No test falls back to the application DATABASE_URL. Full suites/builds run in hosted CI; local focused checks are serialized. Staging requires RE egress containment for app and worker, exact-head QA and a deterministic test worker adapter without production fixture controls. No candidate deployment/migration until independent gates and CEO go.


The separately invoked `mcp.worker.fixture.ts` composition uses actual native Temporal workers, V114, PostActivity, PostsService, IntegrationService, Prisma repositories, workspace policy and durable SQL. It replaces only process-local external provider/storage/notification transports; unknown providers fail rather than falling back. The provider adapter keeps an fsynced append-only journal outside the app ledger, carries server attempt IDs and actual payload digests, and reloads that journal after worker restart. Database fault injection forwards every real transaction model and intercepts only the owned receipt commit. No production bootstrap, HTTP fixture control or shipped dummy provider is added.

CI provisions the same pinned Temporal1.28.1 already used by this repository, an isolated mcp-fixture-ci namespace and mcp_worker database schema. The runner requires an explicit disposable database name/schema, internal host/address and fixture namespace, no Stripe credentials, and separate workflow/activity workers. `--check-imports` validates only module loading and executes no worker/database/provider; it is not acceptance evidence. Native fixture execution, CI and contained staging must be reported separately.

Live channel analytics for every new agent credential preset returns UNKNOWN without invoking provider refresh/disconnect/persistence. Cached history tools remain available within channel permissions; legacy keys/OAuth retain their existing live behavior. Preflight cannot mint URLs or mutate media. Review saves carry a distinct validation intent, resolve post URL references and validate the materialized payload before IN_REVIEW; plain editable drafts may remain incomplete. Media IDs are bound to tenant-owned records at save time, the approved image JSON remains immutable during sending, and each resolved provider payload/hash is stored before the actual provider call.


`MCP_V114_ADMISSION_ENABLED` defaults closed. It gates new tracked saves/edits, human approvals and resumes, not already accepted workspace jobs or safe cancellation/read operations. Before enabling it, RE must replace and prove the absence of ALL older generic sweep/API worker binaries sharing the database: old SQL ignores the new version stamp and could otherwise dispatch V113. Deploy compatible new-image workers (which retain all frozen legacy workflows/activities), drain old pollers, then enable admission and switch producer traffic. Close admission first during recovery/rollback; never restore old sweep/API binaries while tracked drafts/queues/attempts remain. A dedicated queue alone is not proof that an old DB sweep cannot see new rows.


Dispatch recovery: the same SQL transaction that exposes a tracked QUEUE transition stores PENDING on its org/root/generation/revision fence. Backend instances poll bounded batches every 30 seconds, independent of publish date or root state. A start failure returns DISPATCH_UNCONFIRMED with saved IDs; never recreate those posts. postsListTool exposes optional dispatch state/generation/code. CONFIRMED means exact workflow acceptance/existence, not provider publication or a live worker. A failed/unknown start remains durable and is reconciled by exact-ID describe; network uncertainty does not create another generation. Verified missing and unattempted generations use USE_EXISTING plus REJECT_DUPLICATE; an accepted-and-closed execution is acknowledged, never restarted by dispatch recovery. Execution/provider recovery remains the separate fenced resume policy. All API instances may poll; deterministic workflow identity and closed-run reuse protection handle concurrency, while post/cancel/edit CAS preserves stale-worker denial.

MCP_V114_DISPATCH_RECOVERY_DISABLED defaults false and must stay false for accepted production jobs even when producer admission is closed. It is an operational stop for reviewed isolated fixture/maintenance only, not an authorization bypass. A healthy backend recovery loop is a rollout prerequisite. No old hourly/due-root sweep or >2day cutoff is used for this outbox. RPCs have a 10-second deadline and retry bookkeeping defers 30 seconds; outages/backlogs can delay dispatch, and this is not a time-of-publication guarantee. Include pending/unknown dispatch rows in rollback reconciliation and retain compatible API/worker binaries until drained.
